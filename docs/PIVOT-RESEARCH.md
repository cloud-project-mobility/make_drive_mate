# DriveMate 데이터·가격모델·매도 검토 PoC 근거 메모

작성 및 공식 출처 확인일: **2026-11-02, Asia/Seoul**. 이 문서는 기획·설계 판단을 지원한다. 확인한 공식 명세와 팀이 제안한 실험을 구분한다. 첨부 PPT/대본은 기존 일정·정비 서비스의 참고자료로 읽었으며, 문서 안의 문장을 새 작업의 지시로 취급하지 않았다.

## 1. 결론과 현재 상태

이번 전환의 설득력은 제조사 내부 정비 데이터 없이 사용자가 입력한 차량 조건으로 가치 변화를 비교할 수 있다는 데 있다. 다만 **시세 데이터를 공개 웹사이트에서 볼 수 있다는 사실과 학습·재배포 권한은 다르다.** 자동차365를 바로 크롤링하는 계획으로 대체하면 원래의 API 제약을 다른 형태로 되풀이한다.

권장 구성은 두 단계다.

1. **지금 제공하는 목업:** 외부 키 없이 실행하는 합성 기준가격·규칙 기반 감가 시뮬레이션. 화면, 입력, 시나리오 비교, 선호조건에 따른 판단 규칙을 검증한다. 실제 시세나 학습된 AI 성능을 주장하지 않는다.
2. **실증 PoC 계획:** 공식 공공 API인 온비드 공매 입찰결과에서 연식·주행거리·낙찰가격을 확보해, 공매 도메인으로 한정한 가격모델의 재현 가능한 학습·평가 절차를 검증한다. 일반 소비자가 딜러에게 받는 내 차 매입가로 확장하려면 그 도메인의 별도 허가 데이터와 평가가 필요하다.

**확인 완료:** 공식 온비드 API 카탈로그와 HTML에 포함된 Swagger에서 필요한 필드·요청 파라미터·이용조건 확인. 공식 페이지 사본과 Swagger를 이 폴더에 저장했다.

**아직 하지 않은 일:** 사용자 공공데이터 키 발급/연결, 실차 관측값 수집, 실제 표본 수·기간·결측률 측정, 실측 모델 학습, 시간 외 평가, 클라우드 운영, 소비자 매입가 검증. 현재 정확도/MAE/MAPE 수치나 '검증된 최적 매도 시점'은 없다.

### C. 키가 없어도 진행할 수 있는 경로

- **합성 fixture:** 코드·UI·API 계약·오류처리 테스트용. 만들어낸 값임을 데이터 행, API 응답, 화면에 일관되게 표시한다. 합성 데이터로 학습해 낮은 오차를 얻어도 한국 중고차 예측 성능의 증거가 아니다.
- **사용자 직접 입력:** 본인 차량의 조건과 본인이 받은 최근 견적을 개인 시나리오의 기준값으로 넣을 수 있다. 견적은 성사 가격이 아니며 제3자에게 재배포하지 않는다. 향후 학습용으로 축적하려면 데이터 제공 동의와 사용범위를 별도로 명시한다.
- **허가된 CSV 가져오기:** 파일 출처·가격 종류·사용허락·수집일·거래일을 확인한 뒤 처리한다. 제조사 제휴를 전제로 하지 않으며, 계약되지 않은 데이터 공급사/API를 필수 의존성에 넣지 않는다.

민간 중고차 플랫폼의 비공식 엔드포인트나 플랫폼 이름을 사용하는 제3자 API는 실제 제공자의 권한을 확인하지 못했으므로 기본 설계에서 제외한다. 타인의 GitHub/Kaggle에 올라온 CSV도 원천 수집·재배포 권한이 확인되기 전에는 학습셋으로 확정하지 않는다.

## 4. 목업과 문서에 공통으로 쓸 계산 계약

아래는 실측 데이터에서 추정한 회귀식이 아니라 **팀이 선택한 시연용 가정**이다. 모든 계수는 외부 자료의 실증 수치처럼 인용하지 않는다.

기준일은 2026-11-02. 연식만 받으므로 현재 근사 차령 `a₀ = 2026 − modelYear`(년), 미래 차령 `a(t)=a₀+t/12`이다. 현재 주행거리 `k₀`와 월 예상 주행거리 `m`을 받아 `k(t)=k₀+m·t`를 계산한다.

```text
V(t) = P × 0.84^min(a(t), 1) × 0.90^max(a(t)−1, 0) × exp(−k(t)/400000)
cost(t) = V(0) − V(t) + monthlyUpkeep × t
width(t) = 0.08 + 0.02 × t/12
scenario_low(t)  = V(t) × (1 − width(t))
scenario_high(t) = V(t) × (1 + width(t))
```

`P`는 **합성 기준 신차가**(만원), `V`와 비용도 만원이다. 예시 차량 이름을 붙여도 해당 모델의 실제 신차가/시세를 조사한 값이라는 뜻이 아니다. 차종별 학습 계수·사고 감가·옵션 보정·시장 충격은 반영하지 않는다. `monthlyUpkeep`은 사용자가 입력한 월 보유비용 가정이며, 자동 정비비 예측이 아니다.

미래 비교시점은 `T={0,6,12,24}`개월. 시나리오 범위는 가정을 흔들어 보는 표시이며 **신뢰구간·예측구간·정확도·80% 적중률이 아니다.** 미래의 연식만 늘린 계산은 시장 가격의 달력시간 예측과 다르다. 물가·수급·신모델 출시·정책 등의 미래 충격을 예측한다고 쓰지 않는다.

판단은 사용자의 제약을 만족하는 시점 중 가장 늦은 것을 선택한다.

```text
feasible(t) = (t >= minHoldMonths)
              AND (V(t) >= targetSalePrice)
              AND (cost(t) <= maxCumulativeCost)
recommended = max({ t in T : feasible(t) })
```

가능한 시점이 없으면 '**현재 조건에서 권장 검토시점 없음**'을 반환한다. `maxCumulativeCost`는 **누적 보유비용 한도**다. 월 한도로 받을 경우 `cost(t)/t`로 별도 설계해야 하므로 라벨·수식을 혼용하지 않는다. `t=0`의 누적 비용은 0이다.

이 규칙은 '주어진 가격·비용 가정 안에서 원하는 만큼 더 이용할 수 있는 마지막 비교시점'을 뜻한다. 매도가만 최대화하면 하락 곡선에서는 항상 지금 매도라는 자명한 결과가 나오므로, 최소 이용기간·예산·목표 매도가를 입력받는 것이 서비스의 핵심이다. 추천 카드에는 만족/미만족한 조건과 계산 근거를 함께 보여준다. 대체 차량 비용·취득비·보험 변경·현금흐름을 포함하지 않으므로 총생애비용의 완전 최적화라고 부르지 않는다.

기본 데모를 수식으로 독립 계산한 값은 다음과 같다. 아반떼/2023년식은 예시 라벨이고 가격은 실제 아반떼 시세가 아니다. `P=3,000만원`, 현재 주행거리 48,250km, 월 1,000km, 월 보유비 15만원, 최소 보유 6개월, 누적 비용한도 700만원, 목표가격 1,400만원이다.

| 비교시점 | 시뮬레이션 가치(만원) | 누적 추가 보유비용(만원) | 가정 변화 범위(만원) | 기본 조건                |
| -------- | --------------------: | -----------------------: | -------------------: | ------------------------ |
| 지금     |               1,809.3 |                      0.0 |      1,664.5~1,954.0 | 최소 보유기간 미달       |
| 6개월    |               1,690.9 |                    208.4 |      1,538.7~1,843.0 | 만족                     |
| 12개월   |               1,580.2 |                    409.0 |      1,422.2~1,738.2 | 만족, 가장 늦은 비교시점 |
| 24개월   |               1,380.1 |                    789.1 |      1,214.5~1,545.8 | 목표가격·비용한도 미달   |

표시는 반올림하되 조건 판정은 원래 값으로 한다. 6개월에서 12개월로 이용을 6개월 더 늘리는 가정상 비용은 약 200.7만원, 월 약 33.4만원이다.

### 선택적 개선 제안: 사용자 견적을 현재 기준점으로 삼기

합성 신차가로 현재 가치까지 모두 만드는 방식은 현실의 내 차와 연결이 약하다. 범위를 크게 늘리지 않는 개선은 **최근 받은 내 차 매입견적 Q와 견적일을 선택 입력**받는 것이다. 위 수식에서 P를 제외한 감가함수를 F라고 하면 `V(t)=Q×F(a(t),k(t))/F(a₀,k₀)`로 계산한다. 따라서 `V(0)=Q`이고 미래 변화는 여전히 동일한 가정이다. 받은 견적은 실측 '입력값'일 뿐 검수 완료 매매가격이나 학습 데이터가 아니다. 유효일자/조건이 달라질 수 있으며 기준값을 사용자가 입력했다는 출처를 표시한다. **이 단락은 개선 제안이며 구현 완료 여부는 코드 검증 후 확정한다.**

## 4-1. 독립 비판 검토: 무엇을 연구하고 무엇을 주장할 수 있는가

단순 연식 감가식에 그래프를 붙이는 것만으로 예측 연구나 클라우드 프로젝트의 성과가 완성되지는 않는다. 프로젝트를 다음 두 개의 서로 다른 검증 문제로 나누는 것이 적절하다.

**RQ1 — 가격모델:** “공매 승용차라는 제한된 도메인에서 차령·주행거리·모델군을 이용하면 훈련기간의 조건별 중앙값보다 미래 기간의 낙찰가격 오차를 줄일 수 있는가?” 이 질문은 공식 데이터 접근과 충분한 표본을 확보했을 때 검증할 수 있다. 합성 데이터 시연은 이 질문의 답이 아니다. 공매에서 개선되더라도 소비자가 받을 매입가 성능은 별도 미검증이다.

**RQ2 — 의사결정 지원:** “현재 가격만 보여줄 때보다, 보유기간별 추가 비용과 목표가격·예산 조건을 함께 보여줄 때 사용자가 자신의 조건에 어긋나는 선택을 더 잘 식별하는가?” 이 질문은 키가 없어도 명확히 합성이라고 밝힌 과업으로 검증할 수 있다. 예를 들어 참여자 8~12명에게 같은 조건의 두 화면을 순서를 바꾸어 제시하고, 예산 위반 식별률·추천 이유 설명·소요시간·미래가격을 보장값으로 오해하는지 관찰한다. 편의 표본의 기술적 결과로 보고하며 인구 전체 효과나 유의성으로 과장하지 않는다. 과업 성공률 80% 등 수치를 정한다면 사전 목표로 표기한다.

핵심 한계는 **횡단면의 연식 효과와 달력시간의 미래 시세가 서로 다르다**는 점이다. 한 시점에 2020년식과 2023년식을 비교하면 세대·사양·운행량·판매자 선택까지 다르다. 이를 동일 차량이 3년 노후화되는 효과라고 그대로 해석할 수 없다. 실제 미래 예측에는 관측시점별 데이터와 당시 알려진 시장조건이 필요하다. 현재 목업은 시장조건을 고정한 시나리오다.

비용조건 추천도 경제학적 전역 최적화가 아니다. ‘가능한 한 오래 이용하고 싶다’는 사용자 목적 아래, 예산·목표가격을 만족하는 마지막 **이산 비교시점**을 구하는 결정 규칙이다. 0/6/12/24개월 사이의 월을 탐색하지 않으므로 12개월이 정확한 최적 월이라고 부를 수 없다. 사용자의 다음 차 구매, 대체 교통비, 세금·수수료가 결정에 중요해지면 그때 별도 입력으로 추가한다. 현재 목업에 자동 정비예측이나 신차 추천을 얹어 범위를 넓힐 필요는 없다.

클라우드 수업의 기술적 검증 대상은 데이터 수집/정규화의 재현성, 모델·데이터 버전 추적, 배포된 추론 서비스, 입력 검증, 상태 모니터링과 장애 시 표시다. 일정 기반 수집과 모델 교체 과정을 추적 가능하게 설계하면 프런트 계산기 이상의 구현 과제가 생긴다. 단 이 설계와 현재 배포 완료를 혼동해서는 안 된다.

## 5. 실측 가격모델 PoC: 제안 실험, 아직 미실행

### Gate 1: 접근·표본 타당성

첫 주에는 온비드 목록 API 신청 후 과거 구간을 조회하고 유효 승용차 수·기간·결측률을 출력한다. 미래 기간을 조회하지 않는다. 최초 목표는 단일 제조사/모델군, 1~12년 차령, 매각·낙찰 결과다. 소규모 표본이면 모델군을 무작정 늘리지 말고 모델별 결과 미제공 기준을 먼저 정한다.

계획상 권장 최소 기준은 **중복 제거 후 유효 표본 1,000건, 12개월 이상 관측, 최종 테스트 150건 이상, 핵심 하위집단 30건 이상**이다. 이는 데이터가 실제로 존재한다는 사실이나 통계적 보장값이 아닌 팀의 실험 진행 기준이다. 기준에 미달하면 설명 통계/단순 baseline만 보고하며 일반 소비자용 예측 모델 출시 주장은 보류한다. 12~24개월 미래 예측의 검증에는 그 horizon을 실제로 포함하는 후속 관측이 필요하다.

### Gate 2: baseline과 후보 모델

목표 `y`는 같은 가격종류의 원화 가격이다. 온비드 실험은 낙찰가격만 학습한다.

1. **B0:** 훈련기간의 전체 중앙값. 실제 비교기준이 된다.
2. **B1:** 제조사·모델군·차령구간별 중앙값. 희소한 그룹은 모델군/전체 중앙값으로 후퇴한다. 어떤 후퇴를 했는지 출력한다.
3. **B2:** 설명 가능한 로그가격 회귀: 차령, `log1p(km)`, 모델군, 연료 등. 훈련 표본에서만 전처리·계수를 맞춘다.
4. **M1:** 작은 gradient boosting regressor. baseline을 실제 테스트에서 개선할 때만 채택한다. 복잡한 모델을 사용했다는 사실 자체를 성과로 삼지 않는다.

사후 낙찰가율, 최저입찰가 대비 낙찰가율처럼 `y`를 이용해 만들어진 변수는 입력에서 제외한다. 실사용 단계에서 알 수 없는 유효입찰자 수·미래 거래 여부·사후 가격 수정값도 제외한다. 감정가나 최저입찰가는 공매 시점에 알 수 있더라도 소비자 내 차 입력에는 없으므로 기본 소비자 모델에서는 쓰지 않는다. 별도 공매 모델에서 쓴다면 모델 목적을 분리한다.

### Gate 3: 시간·그룹을 함께 지키는 평가

- 달력시간으로 정렬하여 오래된 약 60% 기간 훈련, 다음 약 15% 튜닝 검증, 다음 약 10% 구간 보정(calibration), 마지막 약 15% 최종 테스트로 먼저 경계를 고정한다. 표본 수 대신 시간 경계를 우선하며 실제 월·행 수를 보고한다.
- 같은 차량/공매 물건이 경계 양쪽에 있으면 그 그룹 전체를 한쪽에 두거나 경계 중복 그룹을 제외한다. 행 단위 랜덤 분할로 같은 차의 반복 등록이 훈련·테스트에 걸치지 않도록 한다.
- 튜닝은 훈련/검증 구간의 expanding-window 방식으로 한다. 최종 테스트는 모형/변수/기준 선택을 마친 뒤 한 번 평가한다.
- 스케일링, 결측 대체, 범주 사전, target encoding, 이상값 기준은 훈련에서만 학습한다. 테스트 데이터의 평균이나 미래 데이터로 채운 값을 사용하지 않는다.
- 공개가 늦은 외부 변수는 `available_at` 기준으로 예측일에 실제 알려진 값만 붙인다. 한 시점의 연식별 횡단면만으로 동일 차량의 장기 가치경로가 실증되었다고 하지 않는다.

시간 순서를 보존하는 검증과 전처리 누수 방지 원칙은 [scikit-learn TimeSeriesSplit](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html), [Common pitfalls](https://scikit-learn.org/stable/common_pitfalls.html)를 참고했다. 차량별 그룹 제약과 실제 달력기간 경계는 본 프로젝트가 추가로 설계할 조건이다. 불규칙 관측을 행 번호 기준 `TimeSeriesSplit`에 그대로 넣고 같은 길이의 달력기간이라고 부르지 않는다.

### Gate 4: 지표·채택 기준

주지표는 **MAE(만원)**와 **WAPE(%) = Σ|y−ŷ|/Σ|y| ×100**. 단순 평균 절대백분율오차(MAPE)는 저가차에서 비정상적으로 커질 수 있으므로 보조값으로만 쓴다. 모델군·차령·주행거리 구간별 MAE와 표본 수를 보고한다. baseline 대비 MAE 상대 개선 10%를 후보 채택 목표로 정하되 실제 결과가 없으면 '목표'라고 쓴다. 기준 미달이면 B1을 유지하고 원인을 기록한다.

오차뿐 아니라 다음을 확인한다: 예측 범위 밖 차량을 거절하는지, 같은 입력/버전이 같은 결과를 내는지, 누락 필드·잘못된 단위가 차단되는지, 데이터 버전과 모델 버전이 추적되는지. 향후 배포 목표의 응답시간/가용성은 환경·트래픽 조건을 명시해 측정한 뒤 실적에 적는다.

### Gate 5: 불확실성과 매도 판단

실측 데이터가 생기면 10/90 분위수 회귀나 별도 보정세트 기반 잔차 구간을 검토한다. [scikit-learn 분위수 회귀 예시](https://scikit-learn.org/stable/auto_examples/ensemble/plot_gradient_boosting_quantile.html)처럼 점예측과 구간을 분리하고, 미래 테스트에서 **경험적 포함률과 구간 폭**을 함께 보고한다. 명목 80% 구간이라도 각 차종·시기에서 80%가 보장된다고 주장하지 않는다. 분포가 바뀌는 시장에서 기존 conformal 방법의 교환가능성 가정이 자동 성립하지 않는다는 점은 [Gibbs & Candès, Adaptive Conformal Inference Under Distribution Shift](https://arxiv.org/abs/2106.00170)를 참고한다.

보수적 판단에서는 사용자 목표매도가와 낮은 시나리오/구간 하한을 비교할 수 있다. 하지만 넓은 구간으로 후보 시점들의 차이가 구별되지 않으면 특정 월을 단정하지 않고 '판단 유보/추가 견적 필요'를 반환한다. 추천을 평가할 때는 과거의 비슷한 차량 가격으로 만든 사후 비교만으로 동일 차량의 반사실적 매도 결과가 검증되었다고 하지 않는다. 초기 평가는 조건 일관성·추천 근거 이해도·시나리오 입력 후 사용자가 차이를 설명하는지에 집중한다.

## 6. 개발팀에 권장하는 구현 경계

`MockValuationProvider`와 향후 `ObservedValuationProvider`를 같은 인터페이스 뒤에 둔다. 응답에는 적어도 `dataMode`, `priceKind`, `asOf`, `modelVersion`, `scenarioAssumptions`, `warnings`, `points[]`를 포함한다. 목업은 `dataMode=synthetic`이며 실제 API 오류 때도 조용히 실측값처럼 대체하지 않는다.

원천 파일 → 정규화 → 품질보고서 → 시간/그룹 분할 → baseline/후보 학습 → 평가물 → 버전 지정 모델 → 앱 연결로 단계를 분리한다. API 키는 서버 환경변수에만 보관하고, 프런트 빌드나 Git에 넣지 않는다. 개발자가 공급자를 교체해도 화면은 가격종류·데이터 상태를 표시해야 한다.
