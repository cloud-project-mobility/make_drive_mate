# 차량 카탈로그와 계정 차량 등록

2026-11-04 기준. 차량 사진이 있는 공용 차종 목록과 사용자별 등록 차량을 분리해 저장한다. 차종 카탈로그는 누구나 조회할 수 있고, 계정 차량은 로그인한 사용자만 조회·등록·수정·삭제할 수 있다. 사진 출처와 라이선스는 [차량 사진 안내](VEHICLE-PHOTOS.md)에 있다.

## 화면에서 사용하기

1. 웹 또는 앱에서 차량 등록 화면을 열고 **내 차종 찾기**의 사진 카드를 선택한다. 검색창에서 제조사·모델·세대를 찾을 수 있다.
2. 차량등록증을 기준으로 연식을 입력하고 차량 이름과 누적 주행거리를 확인한다. 카드에 표시된 연식은 이번 카탈로그의 등록 지원 범위이며 전체 판매 기간을 뜻하지 않는다. 같은 연식에 두 세대가 판매된 차종은 세대도 확인한다.
3. **차량 등록하기**를 누른다. 로그인하지 않았다면 **현재는 이 기기에 저장돼요** 안내에 따라 기기에 저장한다. 설정에서 서버에 로그인한 상태라면 계정 DB 저장이 성공한 뒤 기기에도 저장한다. 서버 저장 실패를 기기 저장 성공으로 표시하지 않는다.
4. 다른 기기에서 같은 서버·계정으로 로그인한 뒤 **내 차량 → 계정에 저장한 차량 → 계정 차량 불러오기 → 이 기기에 추가**를 누른다. 이미 같은 ID의 차량이 있으면 중복 추가하지 않는다. 계정과 기기는 각각 최대 3대까지 등록할 수 있다.

지원하지 않는 차종은 직접 입력할 수 있다. 사진 카드를 선택한 뒤 **차종 직접 입력**을 누르면 카탈로그 연결을 해제한다. 기존 `catalogId` 없는 차량과 백업도 계속 사용할 수 있다. 서버 목록을 불러오지 못하면 앱에 포함된 **기본 차량 목록**을 표시하고 연결 실패 안내를 함께 보여준다.

로그인 후 차량 정보 화면에서 저장한 변경사항도 계정에 반영한다. 로그인 상태에서 차량 삭제를 확정하면 해당 계정의 등록 차량과 기기 차량을 삭제한다. 다른 기기에 이미 가져온 데이터가 실시간으로 갱신되는 기능은 아니다. 계정 차량 가져오기는 차량 정보만 추가하며, 주행 기록·계획 등 전체 상태의 백업/복원은 기존 기능을 사용한다. 로그인 전의 기기 차량은 로그인만으로 자동 업로드하지 않는다.

## 저장 구조와 시작 시 seed

- `vehicle_catalog`: 모델·세대·연식·구동 방식, 이미지 객체 키, 원본 URL·저작자·라이선스·대표 이미지 여부·주의사항을 저장한다. 사진 바이너리는 DB에 저장하지 않는다.
- `registered_vehicles`: `user_id + vehicle_id` 복합 기본키로 사용자별 차량을 저장한다. `catalog_id`는 선택값이며 공용 카탈로그를 참조한다. 차량 이름·모델·구동 방식·주행거리·생성/수정 시각을 저장한다. 계정을 삭제하면 해당 차량도 삭제한다.
- 기존 전체 상태 백업은 별도 기능이다. 차량의 선택값 `catalogId`를 백업에 보존하되, 전체 상태 저장만으로 `registered_vehicles`를 자동 갱신하지 않는다.

서버는 `schema.sql`로 테이블 초기화를 마친 후 `backend-spring/src/main/resources/vehicle-catalog/catalog.json`을 읽는다. 시작 전에 JSON 필드, PNG/JPEG 파일 시그니처와 리소스 존재 여부를 검사한다. 같은 ID는 메타데이터를 갱신하고 없는 ID는 추가하므로 재실행할 수 있다. seed에서 빠졌다는 이유로 다른 카탈로그 행이나 사용자 차량·백업을 삭제하지 않는다. 이미지나 메타데이터가 잘못되면 시작을 실패시켜 누락을 알린다.

앱의 기본 목록 `assets/vehicles/catalog.json`과 서버 seed를 함께 유지한다. 앱에는 `assets/vehicles/cutouts/{id}.png`, 서버에는 `vehicle-catalog/images/{id}.png`를 포함한다. 새 차종은 두 JSON, 두 이미지 경로, 앱 이미지 매핑과 출처 표시를 함께 추가하고 검증한다.

## API

모든 경로는 서버 주소 뒤에 붙인다. 공용 목록과 이미지는 인증이 필요 없다.

| 메서드·경로 | 응답·동작 |
| --- | --- |
| `GET /api/v1/vehicle-catalog` | `{ "vehicles": [...], "total": 10 }`. 선택 쿼리 `query`, `manufacturer`, `limit` 제공. 기본·최대 결과 수 100, `total`은 필터에 맞는 전체 개수. |
| `GET /api/v1/vehicle-catalog/{id}` | 카탈로그 항목 하나. 알 수 없는 ID는 404. |
| `GET /api/v1/vehicle-catalog/{id}/image` | 항목에 연결된 패키징 PNG/JPEG. 올바른 MIME과 `Cache-Control: public, max-age=3600`을 반환. 알 수 없는 ID는 404. |
| `GET /api/v1/vehicles` | 인증 필요. `{ "vehicles": [...] }`, 현재 계정 차량만 조회. |
| `PUT /api/v1/vehicles/{id}` | 인증 필요. 같은 ID는 수정, 새 ID는 등록. `{ "vehicle": {...} }` 반환. |
| `DELETE /api/v1/vehicles/{id}` | 인증 필요. 현재 계정에서 삭제하고 `{ "ok": true }` 반환. 반복 삭제 가능. |

카탈로그 항목의 응답 필드는 `id`, `manufacturer`, `model`, `generation`, `yearFrom`, `yearTo`, `powertrains`, `imageUrl`, `imageObjectKey`, `imageSourceUrl`, `imageAuthor`, `imageLicense`, `imageLicenseUrl`, `representative`, `note`다. `imageUrl`은 `/api/v1/vehicle-catalog/{id}/image` 형식의 상대 API 경로다.

인증 API는 기존 로그인 세션의 Bearer 토큰을 사용한다. 등록 요청 예시:

```http
PUT /api/v1/vehicles/vehicle-example-1
Content-Type: application/json
Authorization: Bearer <로그인에서 받은 토큰>
```

```json
{
  "id": "vehicle-example-1",
  "name": "나의 K5",
  "model": "기아 K5 · 2024",
  "powertrain": "HYB",
  "odometerKm": 12500,
  "createdAt": "2026-11-04T00:00:00.000Z",
  "catalogId": "k5-dl3-pe"
}
```

경로와 본문의 차량 ID가 같아야 한다. 직접 입력 차량은 `catalogId`를 생략한다(`null`은 허용하지 않음). 카탈로그 연결 차량은 ID 존재 여부, 모델 이름, 연식 범위, 구동 방식을 서버에서도 검증한다. `model`에는 예시처럼 모델명과 단일 연식을 포함한다. 기존 차량 수정은 등록 한도에 도달해도 가능하며, 동시 신규 등록은 계정 행 잠금으로 최대 3대를 보호한다. 다른 계정의 같은 차량 ID는 별도 데이터다.

이미지 리소스는 검증된 ID와 `.png`/`.jpg` 확장자로만 선택한다. 사용자 입력 URL을 서버에서 가져오거나 사용자 입력 경로를 그대로 읽지 않는다.

## AWS 연결 상태와 배포 범위

현재 AWS 기반 리소스와 차량 이미지 저장 대상은 다음과 같다.

- 리전: `ap-southeast-2`
- 기존 S3 버킷: `drivemate-foundation-20261104-data-zut99t7hjj2z`
- 객체 키: `data/vehicle-catalog/{id}.png` (카탈로그의 `imageObjectKey`와 동일)

`data/vehicle-catalog/`에 PNG 10개와 `catalog.json`, 총 11개 객체를 업로드했다. 모두 HTTP 200 응답을 받았으며 AWS `ListObjectsV2`로 11개 객체의 키와 크기를 재조회해 확인했다. 현재 이미지 API 구현은 S3 다운로드나 공개 버킷 URL 대신 서버에 포함한 파일을 제공한다. S3 객체 존재만으로 원격 DB 등록 API가 배포되는 것은 아니다.

운영 API·RDS 배포는 아직 완료되지 않았다. 실제 운영 DB에 새 테이블과 카탈로그가 생성되는지, 배포한 서버에서 로그인 후 차량 등록·재조회·수정·삭제가 되는지 추가 확인해야 한다. 운영 RDS에서의 SQL 실행, 잠금 동작과 계정 데이터 분리는 아직 검증하지 않았다. AWS 설정을 진행하는 작업과 이 기능의 로컬 검증을 구분한다.

## 검증 기록

2026-11-04, 다른 작업의 빌드 결과와 충돌하지 않는 별도 출력 폴더에서 수행했다.

- `VehicleCatalogApiTest` 9개 + `CoreApiTest` 11개, 총 20개 통과. 목록·검색·최대 결과 수, 이미지 MIME·캐시·안전한 경로, 재실행 seed, 인증·계정 분리, 등록/수정·3대 한도·동시 요청, 잘못된 카탈로그 연결, 계정 삭제와 기존 백업 호환을 포함한다.
- `http://127.0.0.1:18742` 전용 로컬 서버에서 10종 목록과 PNG 10개 응답을 확인했다. 임시 계정으로 차량 등록 → 재조회 → 주행거리 수정 → 재조회 → 차량 삭제 → 계정 삭제까지 실제 HTTP 요청으로 통과했다. 테스트 계정은 정리했다.
- DB는 PostgreSQL 호환 모드의 별도 로컬 H2 파일 DB다. 이 결과는 운영 PostgreSQL/RDS 검증을 대신하지 않는다.

`18742`는 이 작업의 로컬 검증 포트이며 운영 주소가 아니다. 웹 미리보기에서 연결할 때는 설정의 서버 주소로 사용한다. 실제 휴대기기의 `127.0.0.1`은 휴대기기 자신을 가리키므로 배포한 HTTPS 주소나 기기에서 접근 가능한 개발 서버 주소를 별도로 설정해야 한다. 네이티브 기기 실행 결과는 이번 서버 검증에 포함하지 않는다.
